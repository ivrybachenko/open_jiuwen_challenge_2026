- Статус: done
- Дата: 2026-11-12
- Харнесс: `0002`
- Связанная спецификация: —
- Артефакты: `research/experiments/0002-first-wave-predictors/`

## Гипотеза

По признакам, доступным сразу после первой волны текущего харнесса, можно
предсказать:

1. сколько токенов ещё будет потрачено на задачу;
2. сколько ещё ходов потребуется;
3. решаема ли задача (в синтетической разметке — `solvable` / `impossible`);
4. получится ли закрыть задачу второй волной и сколько это будет стоить.

Отдельно проверяются две гипотезы.

**Лексические маркеры.** Маркеры неуверенности, удивления и противоречия в
рассуждении модели (`hmm`, `wait`, `actually`, `all right`, `fine`,
`it must work`, `wow`, `contradictory`, `not sure`, `stuck`, `give up` и
т.п.) улучшают предсказание. Для этого признаки делятся на наборы `turn`
(без новых маркеров) и `turn_keywords` (с ними); сравнение идёт на одних и
тех же разбиениях и моделях.

**Перенос на новые задачи.** Горизонтальное разбиение (все категории, доля
задач) завышает качество по сравнению с вертикальным (обучение на двух
категориях, валидация и тест — на других). Если при вертикальном разбиении
метрики падают, а прирост от статических признаков задачи исчезает, модель
переобучается на синтетический генератор и не готова к датасету
организаторов.

Гипотеза считается подтверждённой, если на отложенных задачах:

- регрессия остатка токенов заметно лучше константы и медианы по категории
  (MAE и Spearman);
- вероятность успеха второй волны предсказывается лучше, чем доля успехов
  по категории (ROC-AUC / PR-AUC);
- классификатор решаемости лучше константы (ROC-AUC / PR-AUC);
- признаки только поведения первого хода дают результат, сопоставимый с
  добавлением статических признаков задачи;
- добавление лексических маркеров даёт измеримый прирост относительно
  `turn` хотя бы на одной из целевых величин, и этот прирост не объясняется
  только длиной рассуждения;
- вертикальное разбиение не обрушивает метрики относительно горизонтального.

Оценка привязана к версии харнесса: промпты, лимиты и способ учёта токенов
меняются между версиями. Поэтому в обучение идут только записи `0002`, а
`trajectories_default.jsonl` от `0001` в этом эксперименте не используется.

## Условия

- Модель: `qwen3.6-35b-a3b`.
- Датасет: `data/task`, 240 синтетических задач (160 `solvable`,
  80 `impossible`). Организаторы используют другой датасет, поэтому
  синтетические задачи — только проверка метода, не финальный критерий.
- Сбор данных: один прогон текущего харнесса `0002` по всем 240 задачам,
  тремя параллельными процессами (по ~80 задач), лимиты волн по умолчанию
  (1000 / 4000 токенов), `--wave2-max-tasks 0`, без бюджета.
- `run_id`: `exp0002-full-v0002-20261112-s0`, `...-s1`, `...-s2`.
- Записи: `data/trajectories/exp0002-shard{0,1,2}/bash_attempts.jsonl`
  (в git не хранятся). Получилось 355 записей, 240 групп
  `(run_id, task_id)`, по одной на задачу.
- Внешняя проверка: 92 более ранних первых хода `0002` из
  `data/trajectories/bash_attempts.jsonl` на 12 задачах. Эти задачи
  принудительно попадают в test горизонтального разбиения, чтобы модель не
  видела их в обучении.
- Горизонтальное разбиение: 12 внешних задач — test; остальные 228 делятся
  60/20/20 со стратификацией по `task_type × solvable`. Все прогоны одной
  задачи попадают в одну часть.
- Вертикальные разбиения: обучение на двух категориях, валидация и тест — на
  двух других. Сделаны четыре ротации, чтобы каждая категория побывала в
  test:

  | Ротация | train | val | test |
  | --- | --- | --- | --- |
  | search | coding, data_analysis | math | search |
  | coding | data_analysis, math | search | coding |
  | data_analysis | math, search | coding | data_analysis |
  | math | search, coding | data_analysis | math |

- Целевые величины после первой волны:
  - `remaining_tokens` — токены всех последующих ходов;
  - `remaining_turns` — число последующих ходов (в `0002` это 0 или 1);
  - `wave2_cost` — токены второй волны, только для задач без ответа в первой;
  - `wave2_any_answer` — появился ли непустой ответ во второй волне;
  - `wave2_success` — зачтён ли ответ оценщиком (`correctness.json`);
  - `solvable` — синтетическая разметка задачи;
  - `solved_correctly` — зачтён ли ответ в этом прогоне.
- Признаки:
  - `turn` — только поведение первой волны: расход, обрыв по лимиту,
    рассуждение, форма скрипта, код возврата, наличие ответа и его вид;
  - `turn_overview` — `turn` + размер обзора каталога;
  - `turn_keywords` — `turn` + частоты и флаги лексических маркеров,
    нормированные на длину текста (на 100 слов);
  - `full` — `turn_keywords` + `turn_overview` + длина инструкции и
    статистика workspace. Статические признаки сильнее всего подвержены
    переобучению на генератор.
- Модели: Ridge, Random Forest, HistGradientBoosting; для классификации —
  Logistic Regression, Random Forest, HistGradientBoosting. Гиперпараметры
  выбираются на validation, test не используется для выбора.
- Метрики: MAE, RMSE, MedAE, R², Spearman, ROC-AUC, PR-AUC, accuracy,
  balanced accuracy, Brier, log-loss; доверительные интервалы — bootstrap по
  test-строкам (300 повторов для горизонтального разбиения, 100 для
  вертикальных).
- Обучение: `scikit-learn` установлен только в `harness/.venv`
  (`uv pip install --python harness/.venv/bin/python scikit-learn`); в
  зависимости харнесса он не входит.
- Команды:

### Ограничения

- Синтетический датасет и один прогон на задачу. Вертикальное разбиение
  проверяет перенос на новую категорию, но не на новый генератор и не на
  датасет организаторов.
- В `0002` всего две волны, поэтому `remaining_turns` — бинарная величина.
  Для честной регрессии числа ходов нужен харнесс с тремя и более волнами,
  но тогда оценка будет привязана уже к другой версии.
- Условные цели (`wave2_cost`, `wave2_success`, `wave2_any_answer`) имеют
  всего 99 наблюдений; validation шумная, и выбор гиперпараметров на ней
  легко переобучается. Это видно по `wave2_any_answer`: ROC-AUC на
  validation 0,67–0,94, на test — 0,17–0,42.
- Статические признаки (`ins_*`, `ws_*`) отражают устройство синтетических
  задач. В частности, `ins_has_impossible` и длина инструкции могут косвенно
  кодировать формулировки невыполнимых задач генератора, а не свойство
  реальной задачи. Их нельзя переносить в зачётный харнесс без проверки на
  реальных задачах.

## Вывод

Гипотеза подтверждена частично.

1. **Остаток токенов** предсказуем лучше константы и медианы по категории,
   но не лучше простого правила «0, если ответ уже есть, иначе медиана».
   Модель выигрывает в ранжировании (Spearman 0,86 против 0,83 на
   горизонтальном тесте), но проигрывает в MAE на большинстве вертикальных
   разбиений. Для выбора задач этого недостаточно.
2. **Остаток ходов** в `0002` не требует модели: это детерминированное
   правило по `answer_kind`. Обученная регрессия только добавляет ошибку.
3. **Классификатор решаемости** работает на горизонтальном разбиении
   (ROC-AUC 0,80–0,97), но на вертикальном среднее падает до 0,68–0,71, а на
   `coding` — до 0,56. Причина — статические признаки задачи: `full` даёт
   +0,235 ROC-AUC на горизонтальном тесте и почти ничего на вертикальном.
   Классификатор **не готов** к новым задачам и категориям.
4. **Успех второй волны** предсказывается умеренно (ROC-AUC 0,68–0,70 для
   поведенческих признаков), но `full` на вертикальном тесте падает до
   0,562. **Стоимость второй волны** не предсказывается: медиана лучше или
   не хуже модели. **Факт появления ответа** во второй волне не
   предсказывается.
5. **Лексические маркеры** гипотезу не подтверждают. Половина предложенных
   фраз не встречается вовсе; `wait` и `actually` часты, но прирост
   нестабилен. Работает только семейство `no_solution`/`impossible`, уже
   присутствующее в признаках.
6. **Горизонтальное разбиение завышает качество.** Вертикальное разбиение
   обязательно для проверки переноса; на нём модель с статическими
   признаками теряет большую часть прироста.

## Решение

1. Не заменять эвристику отбора второй волны обученной моделью в `0002`.
   Текущая прозрачная эвристика остаётся; спецификация изменения не
   создаётся.
2. Для `remaining_turns` использовать детерминированное правило:
   вторая волна нужна, если `answer_kind` первой волны — `none` или
   `impossible`. Регрессию для этой цели не обучать.
3. Для `remaining_tokens` оставить baseline «0, если ответ есть, иначе
   медиана» как точку сравнения. Если обучать модель, то только на
   поведенческих признаках (`turn`), с сильной регуляризацией и проверкой на
   вертикальном разбиении; статические `ins_*`/`ws_*` не использовать.
4. Для `wave2_cost` и `wave2_any_answer` данных недостаточно: 99 условных
   наблюдений и один прогон на задачу. Нужен сбор 3–5 прогонов на задачу и
   больше категорий, иначе validation выбирает переобученную модель.
5. Повторить эксперимент на задачах организаторов или на отложенном
   семействе синтетических задач, которого нет в обучении. Без этого
   «готовность к новым задачам» не доказана.
6. Отрицательный результат сохранить: он избавляет от внедрения
   классификатора, который на горизонтальном тесте выглядит почти идеальным,
   а на вертикальном падает до уровня «лучше случайного».
