# AGENTS.md

## Приоритет документов

При конфликте требований: регламент соревнования → конституция →
`specification/behavior/` → остальная документация.

## Документы

| Что нужно | Где смотреть |
| --- | --- |
| Собрать, запустить, понять структуру проекта | `README.md` |
| Требования организаторов | `challenge_info/problem_statement.md` |
| Правила всего проекта | `specification/constitution/README.md` |
| Уровни спецификации и куда что писать | `specification/README.md` |
| Текущее поведение решения | `specification/behavior/README.md` |
| Оформить изменение поведения | `specification/changes/README.md`, `specification/changes/_template/spec.md`, `specification/changes/_template/tasks.md` |
| Оформить проверку гипотезы | `research/experiments/README.md`, `research/experiments/_template.md` |
| Оформить обзор литературы | `research/literature_review/README.md`, `research/literature_review/_template/protocol.md` |
| Проверить решение и прочитать отчёт | `evaluation/README.md` |

Регламент и конституция обязательны; остальные документы открывай по
потребности. Для изменения поведения открой также файл
`specification/behavior/` по затронутой области.

## Границы

- Меняешь наблюдаемое поведение или контракт — сначала `spec.md`, потом код.
- Рефакторинг без изменения поведения и правка текста спецификацию не требуют.
- Замороженный `spec.md` не редактируется: новое изменение ссылается на него.
- Новые правила процесса не вводятся через `AGENTS.md`: сначала конституция
  или спецификация изменения.
- Если правило мешает задаче, меняй спецификацию, а не обходи его молча.

## Порядок работы

1. Определи тип задачи:
   - правило проекта → `specification/constitution/` и строка в таблице состава;
   - поведение или контракт → `specification/changes/NNNN-slug/`;
   - гипотеза → `research/experiments/NNNN-slug.md`;
   - обзор литературы → `research/literature_review/NNNN-slug/`;
   - рефакторинг, документация, вопрос или исследование → спецификация не
     нужна.
2. Для гипотезы запиши гипотезу, условия и план замера в журнал до запуска.
   Отрицательный результат сохраняется.
3. Для изменения поведения напиши `spec.md` по шаблону до кода: дельта,
   проверяемые критерии приёмки, затрагиваемый файл в
   `specification/behavior/`.
4. Составь `tasks.md` по шаблону: каждая задача ссылается на критерий
   приёмки.
5. Реализуй изменение и проверь каждый критерий; запиши результат проверки
   в `spec.md`.
6. Обнови затронутый файл `specification/behavior/`. Если область новая,
   добавь файл и строку в `specification/behavior/README.md`.
7. Заморозь изменение: статус `implemented`, `tasks.md` удали или пометь
   архивом, в новом `spec.md` укажи `Supersedes: NNNN`, в старом —
   `Superseded by: NNNN`.
