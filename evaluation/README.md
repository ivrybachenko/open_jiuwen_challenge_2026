# Оценка решения

Пакет `evaluation` проверяет, насколько хорошо харнесс решает задачи. Код
использует только стандартную библиотеку Python (3.9+) и не требует
установки дополнительных зависимостей. Для запуска самого харнесса нужен
интерпретатор с `openjiuwen` — по умолчанию берётся `harness/.venv/bin/python`.

## Компоненты

| Команда | Что делает |
| --- | --- |
| `python -m evaluation.answer_evaluator` | проверяет ответ одной уже решённой задачи (`unittest` / `exact_int` / `exact_str`) |
| `python -m evaluation.harness_task_checker` | запускает харнесс на одной задаче и печатает «решено / нет, токены, время» |
| `python -m evaluation.harness_task_set_checker` | запускает харнесс на наборе задач и печатает «баллы, токены, время» |
| `python -m evaluation.dockerfile_checker` | собирает Docker-образ, проверяет размер/время сборки и прогоняет минимальный набор задач в контейнере |
| `python -m evaluation.repo_size_checker` | измеряет размер репозитория и сверяет его с лимитом 100 МБ без `.git` |
| `python -m evaluation.commit_harness_version` | полный замер версии: 5 прогонов каждой задачи и 5 прогонов набора `example`, дописывание результатов в датасеты |

Все команды пишут JSON-отчёт в `out/reports/` (каталог можно переопределить
флагом `--out`) и возвращают код `0`, если проверка успешна, `1` — если задача
не решена / не выполнено условие, `2` — если проверку не удалось запустить.

## Требования к окружению

- `LLM_API_KEY` — для всех команд, которые запускают харнесс. Ключ передаётся
  подстановкой bash, чтобы Python не читал и не печатал исходную переменную:

  ```bash
  LLM_API_KEY="$NEURAL_DEEP_API_KEY" \
  python -m evaluation.harness_task_checker --task coding/solvable/0001
  ```

- `LLM_BASE_URL` оценщики подставляют сами: `https://api.neuraldeep.ru/v1`
  захардкожен в `evaluation/common/runner.py`. В самом харнессе URL нет — он
  по-прежнему читает `LLM_BASE_URL` из окружения.
- `TASKS`, `OUT`, `TOKEN_BUDGET`, `LLM_MODEL` — необязательны; чекеры передают
  соответствующие значения флагами.
- Docker — только для `dockerfile_checker`.

## Версия и run_id

С `--record` обязательно передаётся `--harness-version`. Скрипт читает версию
из `harness/pyproject.toml` и завершается с ошибкой, если она не совпадает с
указанной:

```bash
python -m evaluation.harness_task_checker \
    --task coding/solvable/0001 --harness-version 0001 --record
```

Каждый записанный результат получает свой `run_id` — случайный UUID. Поэтому
две строки в датасете не могут иметь одинаковый `run_id`, а два запуска
одного и того же чекера добавляют две разные строки. `run_id` можно задать
вручную через `--run-id`; если он уже занят другой задачей или набором,
запись завершится ошибкой. Этот же `run_id` чекеры передают в харнесс, и он
попадает в траекторию (`harness.run_id` в JSONL, `run_id` в YAML), поэтому
конкретная траектория соединяется со строкой датасета.

## Запись датасетов

Флаги `--record` у чекеров обновляют датасеты в `data/`:

- `harness_task_checker --record` → `data/harness_task_score/harness_v_<version>.tsv`;
- `harness_task_set_checker --record` → `data/harness_task_set_score/harness_v_<version>.tsv`;
- `dockerfile_checker --record` → тот же датасет наборов, но по результату
  контейнерного прогона.

## Полный замер версии

```bash
LLM_API_KEY="$NEURAL_DEEP_API_KEY" \
python -m evaluation.commit_harness_version --harness-version 0001
```

Скрипт:

1. проверяет версию в `harness/pyproject.toml`;
2. проверяет, что в `data/harness_info/harness_info.tsv` есть запись для этой
   версии (иначе — ошибка);
3. дописывает результаты в `harness_v_<version>.tsv` в обоих датасетах;
   существующие строки сохраняются;
4. прогоняет харнесс 5 раз на каждой задаче из `data/task` и 5 раз на наборе
   `example`;
5. пишет каждую строку результатов со своим уникальным `run_id`.

Параметры `--runs`, `--max-tasks`, `--skip-set` позволяют сделать быстрый
smoke-тест. Флаг `--tasks-from <task-set.yaml>` ограничивает per-task прогоны
задачами из набора; без него берутся все задачи из `data/task`. Очистки
датасетов нет: каждая записанная строка получает свой `run_id`. Описание
полей — в README соответствующих каталогов `data/`.

## Что именно проверяется

1. **Ответ.** Харнесс пишет `answer.txt` в `workspace/` и в корень задачи.
   Оценщик читает оба места; для `unittest` дополнительно запускает
   `test*.py` в `workspace/` и требует код возврата `0`.
2. **Подмена тестов.** Перед запуском чекеры хешируют `test*.py` и после
   прогона проверяют, что тесты не были изменены или удалены. Отключить это
   можно флагом `--allow-test-edits`.
3. **Стоимость.** Токены и стоимость берутся из `solutions.json`
   (`input_tokens`, `output_tokens`, `cost`). Если поля `cost` нет, оно
   считается по формуле соревнования: `output + ceil(input / 10)`.
4. **Время.** Замеряется время работы процесса харнесса (или `docker run`).
5. **Траектории.** Чекеры передают `--trajectories-dir <repo>/data/trajectories`
   и сохраняют полные траектории openJiuwen для обучения предсказателя
   сложности: машинный `trajectories_default.jsonl` и читаемый
   `readable/*.yaml`. Формат — в
   [data/trajectories/README.md](../data/trajectories/README.md).

## Важно

Чекеры не меняют исходный датасет: задачи копируются во временный каталог,
харнесс работает с копией. После прогона временный каталог удаляется, если не
указан `--keep`.
