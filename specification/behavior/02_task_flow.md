# Обработка задач

- Состояние: реализовано
- Читатель: разработчик и coding-агент; организатор читает `README.md`
- Проверки: [таблица проверок](#как-проверить)

## Обнаружение задач

- Задачи — непосредственные подкаталоги `--tasks-dir`, в каждом есть
  `task.json`.
- Каталоги читаются в лексикографическом порядке имён.
- `task.json` читается как UTF-8 с необязательным BOM. Символическая ссылка
  `task.json` за пределы каталога задачи не читается.
- Некорректный `task.json` пропускается с предупреждением в лог: файл не
  читается, содержит не JSON-объект или поле не приводится к строке/числу.
  Одна плохая задача не останавливает остальные.
- Из `task.json` используются поля `task_id`, `task_type`, `instruction`,
  `reward`, `expected`, `check`. Если `task_id` нет, берётся имя каталога.
  `expected` и `check` не влияют на решение и расход.
- `reward` приводится к конечному неотрицательному числу; нечисловое,
  `NaN`, бесконечное или отрицательное значение даёт `0` и предупреждение.
- Повторяющийся `task_id` пишется в лог предупреждением. Контракт требует
  уникальности: идентификатор — ключ состояния и `solutions.json`.
- Рабочий каталог задачи — `<task>/workspace`, если он существует и после
  разрешения символических ссылок остаётся внутри `<task>`; иначе корень
  задачи.

## Волны

Решение идёт волнами, по умолчанию до восьми (`--max-waves`).

1. **Волна 1.** Каждая задача получает ровно один ход модели с лимитом
   `--wave1-max-tokens` (1000). Если после исполнения скрипта появился
   непустой `answer.txt`, задача временно закрывается; повторного хода в этой
   волне нет. Задачи идут по убыванию `reward`, при равенстве — по `task_id`.
2. **Волны 2–8.** Из незавершённых задач выбираются перспективные по
   `reward · P(успех) / ожидаемая стоимость`. Каждая выбранная задача
   получает один дополнительный ход с `--wave2-max-tokens` (4000). Число
   задач ограничено `--wave2-max-tasks` (50); при нехватке бюджета волна
   может покрыть только часть кандидатов.

Вторая волна продолжает историю первой: агент видит свой скрипт и вывод его
исполнения. Если первая волна писала `IMPOSSIBLE`, задача может быть выбрана
снова: тогда `answer.txt` удаляется, а в сообщении появляется предупреждение
перепроверить вывод. Если вторая волна не дала нового ответа, прежний ответ
восстанавливается.

## Порядок обработки

- Внутри волны задачи решаются последовательно, по одной.
- Порядок первой волны — по убыванию `reward`, при равенстве — по
  `task_id`; сложность и ожидаемая стоимость до решения не используются.
- Перед каждым ходом проверяется, не исчерпан ли бюджет. Если исчерпан,
  обработка прекращается.
- Флаг `--max-tasks N` ограничивает список первыми `N` задачами после
  сортировки по `reward`.
- Параллельные сессии не используются, хотя регламент допускает до пяти.
- После трёх подряд ошибок модели волна останавливается.

## Жизненный цикл хода

1. Задача загружает состояние из
   `<agent-workspace>/<task_id>/state.json`.
2. Если состояния нет, удаляются старые `answer.txt`, строится обзор и
   сохраняется начальное состояние.
3. Модель получает историю сообщений и лимит волны.
4. Ответ превращается в bash-скрипт, исполняется в рабочем каталоге.
5. Харнесс проверяет `answer.txt` в рабочем каталоге и корне задачи.
6. Токены списываются, состояние и `solutions.json` перезаписываются.
7. Если ответ появился, задача считается завершённой для этой волны.

Если задача падает с исключением, харнесс записывает её с пометкой
`model_error` или `solver crashed` и переходит к следующей. Одна сломанная
задача не останавливает весь прогон.

Если после списания расхода бюджет превышен, текущий ход всё равно
записывается в `solutions.json`, после чего прогон останавливается. Поэтому
фактический расход может превысить лимит на стоимость одного хода.

## Известные ограничения

- Волны 3–8 используют модель и лимит второй волны; отдельных моделей на
  каждую волну по умолчанию нет.
- Нет проверки правильности ответа перед второй волной: любой непустой
  `answer.txt` считается ответом.
- Нет пропуска задач по признаку невыполнимости: поля `solvable` и
  `impossible` из `task.json` харнесс не читает.
- `task_id` должен быть уникальным: он используется как идентификатор
  состояния и ключ в `solutions.json`.

## Как проверить

Общие команды и флаги — в [`evaluation/README.md`](../../evaluation/README.md).

| ID | Уровень | Что подтверждает | Проверка | Ожидаемо |
| --- | --- | --- | --- | --- |
| V-1 | быстрая | первая волна сортирует задачи по убыванию `reward`, при равенстве — по `task_id` | `cd harness && uv run python -m unittest test.test_bash_agent` | тест `test_wave1_order_by_reward_then_task_id` OK |
| V-1a | интеграционная | задачи находятся и обрабатываются | `python -m evaluation.harness_task_set_checker --task-set data/task_set/example.yaml` | в отчёте все задачи набора; порядок — по `reward` |
| V-2 | быстрая | волна 1 делает один ход, волна 2 — только для незавершённых | `cd harness && uv run python -m unittest test.test_bash_agent` | тесты волн OK |
| V-3 | интеграционная | одна задача проходит полный цикл | `python -m evaluation.harness_task_checker --task coding/solvable/0001` | в отчёте есть ответ, токены и время; процесс завершился штатно |
| V-4 | быстрая | BOM, нечисловой `reward` и не-объект в `task.json` не останавливают загрузку; `solvable`/`impossible` не читаются | `cd harness && uv run python -m unittest test.test_loader` | все тесты OK, плохая задача пропущена или получает `reward=0` |

Отчёт показывает, был ли ответ, сколько потрачено токенов и сколько занял
прогон.
