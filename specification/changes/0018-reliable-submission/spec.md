## Зачем

Три дефекта теряют результат в условиях запуска жюри. Общая причина одна:
харнесс зависит от окружения, которое регламент не гарантирует, и не доводит
до конца то, что агент уже сделал.

1. **`OUT` задан, но не смонтирован.** Регламент обещает переменную `OUT`, а
   приведённая там команда `docker run` её не передаёт и не монтирует. Если
   проверяющая система всё же выставит `OUT` в путь, недоступный на запись в
   read-only контейнере, `SolutionsStore._flush` падает с `OSError`, прогон
   завершается после первой задачи, `solutions.json` не создаётся.
2. **Исполняется только последний fenced-блок.** Модель иногда возвращает
   несколько bash-блоков вместо одного. `extract_script` брал последний, и
   скрипт вида «правка файла → запуск тестов → `echo DONE > answer.txt`»
   исполнялся как один `echo DONE`. Ответ сдан, тесты не исправлены, задача
   не засчитана, а вторая волна не запускается, потому что ответ уже есть.
   Замер: 1 из 6 свежих прогонов `coding_0003` дал `answer=DONE` при падающих
   тестах.
3. **Относительный путь к скрипту.** Копия скрипта в рабочем каталоге
   передавалась `bash` относительным путём, а `cwd` процесса — рабочий
   каталог задачи. При относительном `--tasks-dir` скрипт не находился
   (`exit 127`), и ход тратился впустую.

Следствие — риск на отборочном прогоне из двух задач: одного провала
достаточно для снятия.

## Что меняется

1. Если файл решений нельзя записать по основному пути (`--out` или `OUT`),
   харнесс пробует запасные: `<tasks-dir>/solutions.json`, затем
   `/tmp/solutions.json`. Ошибка записи не прерывает прогон; после первой
   успешной записи по запасному пути харнесс продолжает писать туда, чтобы не
   терять файл при каждом ходе.
2. При старте `solutions.json` читается по тем же путям по порядку, поэтому
   прогон восстанавливается и из запасного файла.
3. Все fenced-блоки bash в ответе модели склеиваются в порядке появления и
   исполняются одним скриптом. Промпт требует ставить запись `answer.txt` в
   конец последнего блока и сдавать ответ, даже если тесты уже проходят.
4. Предупреждение второй волны явно требует записать `answer.txt`, если
   тесты уже проходят.
5. Скрипт запускается по абсолютному пути, независимо от текущего каталога
   процесса.

## Критерии приёмки

- [x] AC-1: при `OUT` в недоступном на запись пути и записываемом каталоге
      задач прогон не падает, `solutions.json` появляется в каталоге задач,
      процесс завершается с кодом 0.
- [x] AC-2: ответ из нескольких bash-блоков исполняется целиком и по порядку;
      блок, сдающий ответ, выполняется последним.
- [x] AC-3: системный промпт и предупреждение второй волны требуют записать
      `answer.txt`, даже если тесты уже проходят.
- [x] AC-4: при относительных `--tasks-dir` и `--agent-workspace` скрипт
      исполняется и создаёт `answer.txt`.
- [x] AC-5: существующие тесты проходят; контейнерный прогон минимального
      набора решает обе задачи в серии прогонов.

## Вне рамок

- Третья волна и повторные вызовы модели: причина сбоя была в исполнении
  скрипта, а не в числе ходов.
- Автоматическая сдача ответа харнессом по видимым тестам или по `expected`:
  харнесс по-прежнему не проверяет правильность и не читает скрытые тесты.
- Изменение бюджета, выбора второй волны и формулы стоимости.
- Правка команды запуска в регламенте организаторов.

## Ограничения

- Запасной путь не гарантирует, что жюри найдёт файл: если `OUT` не смонтирован
  и жюри читает только `OUT`, задача всё равно не будет засчитана. Запасной
  путь сохраняет прогон и `answer.txt`, а не заменяет контракт `OUT`.
- Склейка блоков исполняет всё, что модель пометила как bash; текст без
  fences по-прежнему исполняется as-is.
- Порядок блоков сохраняется, поэтому модель обязана ставить сдачу ответа
  последней; промпт это требует.

## Проверка

- `cd harness && uv run python -m unittest discover -s test`.
- `python -m evaluation.dockerfile_checker --skip-build --task-set minimal.yaml`
  — серия прогонов, обе задачи решены.
- `python -m evaluation.dockerfile_checker --skip-build --task-set example.yaml`
  — регресс на наборе из 8 задач.
- Ручной прогон контейнера с `-e OUT=/srv/jury/out` без монтирования:
  в логах предупреждение, в `/data/tasks` есть `solutions.json`, exit 0.

Результат: 68 тестов OK; контейнерный прогон `minimal.yaml` — 4 прогона из 4
с обеими решёнными задачами; `example.yaml` — 7/8 (было 6/8). Подробнее
в `tasks.md`.

## Риски и откат

- Склейка блоков может исполнить лишний блок, если модель показала
  альтернативный вариант. Это ближе к намерению модели, чем исполнение только
  последнего блока; откат — вернуть выбор последнего блока.
- Запасной путь может скрыть ошибку конфигурации `OUT`. Поэтому смена пути
  пишется в лог как `WARNING` с обоими путями.
- Откат: вернуть `blocks[-1]`, запись только по `OUT` и относительный путь.
