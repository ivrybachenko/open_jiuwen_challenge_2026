# Спецификации изменений

Одна директория — одно изменение наблюдаемого поведения или контракта.
Спецификация пишется до кода и после реализации становится историей решения.

## Когда спецификация нужна

- новый или изменённый CLI-флаг, формат файла, поведение агента;
- изменение планировщика, бюджета или стратегии выбора задач;
- багфикс, который меняет наблюдаемое поведение;
- изменение, затрагивающее Docker-образ, зависимости или запуск.

## Когда спецификация не нужна

- рефакторинг без изменения поведения и контракта;
- эксперимент, который ещё не решили внедрять;
- правка текста документации или комментариев.

Для таких изменений достаточно соблюдать конституцию, а результат
эксперимента записать в
[`../../research/experiments/`](../../research/experiments/README.md).

## Структура

```
changes/
  _template/
    spec.md          # шаблон спецификации изменения
    tasks.md         # шаблон плана выполнения
  NNNN-slug/
    spec.md
    tasks.md
```

- `NNNN` — сквозной номер из четырёх цифр: `0001`, `0002`, …
- `slug` — короткое имя изменения латиницей через дефис.
- `spec.md` описывает дельту: что и почему меняется относительно текущего
  поведения. Это не описание всей системы.
- `tasks.md` — план выполнения. Временный артефакт, а не долгоживущий
  TODO-список.
- Если для изменения нужен отдельный технический план, он добавляется в ту же
  директорию как `plan.md`; отдельного шаблона нет.

## Жизненный цикл

```
draft → accepted → implemented
                 ↘ rejected
```

- **draft** — спецификация пишется, критерии уточняются.
- **accepted** — критерии согласованы, можно приступать к реализации.
- **implemented** — критерии проверены, текущее поведение обновлено.
- **rejected** — решили не делать; причина остаётся в спецификации.

После `implemented`:

- `spec.md` замораживается и остаётся историей решения. Он не обновляется при
  последующих изменениях поведения.
- `tasks.md` удаляется: его история есть в git. Если команде нужен аудит, файл
  можно оставить с пометкой «архив, не поддерживается».
- Затронутый файл в [`../behavior/`](../behavior/README.md) обновляется: именно
  он описывает текущее состояние.
- Новое изменение той же области оформляется новым `spec.md`. В нём
  указывается `Supersedes: NNNN`, а в старом — `Superseded by: NNNN`.

## Правила

- Спецификация пишется до кода. Спецификация после кода — это описание, а не
  SDD.
- Каждый критерий приёмки проверяем: команда, тест, замер или наблюдаемое
  поведение.
- Каждая задача в `tasks.md` ссылается хотя бы на один критерий приёмки.
- В спецификации указано, какой файл поведения она меняет.
- Изменение не считается завершённым, пока критерии не отмечены, поведение не
  обновлено и результат проверки не записан.
- Если изменение нарушает конституцию, сначала меняется конституция или само
  изменение, а не обходится правило.
