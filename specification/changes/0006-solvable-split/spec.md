## Зачем

Деление на `easy`/`medium`/`hard` субъективно: задачи придумывались без
единой шкалы, и метка не используется ни харнессом, ни оценщиком. При этом
она попадает в идентификаторы датасетов и в примеры команд, создавая ложное
впечатление измеренной сложности. Для регламента и оценки важно только одно
деление: задача решаемая или нерешаемая.

## Что меняется

- Каталоги задач переходят от `data/task/<type>/<difficulty>/<id>` к
  `data/task/<type>/solvable/<id>` и `data/task/<type>/impossible/<id>`.
- Решаемые задачи внутри типа перенумеровываются: бывшие `easy`, `medium` и
  `hard` идут подряд в `solvable`.
- Идентификаторы задач в `data/task_set/*.yaml` и исторические строки
  `data/harness_task_score/*.tsv` переписываются на новые пути.
- Примеры команд, README пакетов оценки и тестовые фикстуры обновляются.
- `task.json`, `reward`, условия и проверки задач не меняются.

## Критерии приёмки

- [x] AC-1: под `data/task` нет каталогов `easy`, `medium`, `hard`.
- [x] AC-2: у каждого типа есть `solvable` и `impossible`; все задачи с
  `solvable: false` лежат только в `impossible`.
- [x] AC-3: все наборы из `data/task_set` ссылаются на существующие задачи.
- [x] AC-4: в `data/harness_task_score` не осталось старых путей.
- [x] AC-5: быстрые тесты и проверка условий задач проходят.

## Вне рамок

- Переклассификация задач по содержанию.
- Изменение `task_id` внутри `task.json`.
- Изменение `reward`, условий или проверок.

## Ограничения

Исторические замеры сохраняются, но их идентификаторы задач меняются вместе с
путями. Строки нельзя сопоставить со старым деревом без таблицы соответствия
из этого изменения.

## Проверка

- `python3 -m unittest discover -s evaluation/test -t .` — быстрые тесты.
- Загрузка всех наборов через `evaluation.common.tasks`.
- Поиск старых путей по репозиторию.

## Риски и откат

Риск: ссылка на старый путь останется в документации или тесте. Ловится
поиском и тестами. Откат — вернуть каталоги и старые пути в датасетах; данные
задач не меняются, поэтому откат безопасен.
