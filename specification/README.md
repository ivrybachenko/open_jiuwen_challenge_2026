# Спецификация проекта

Спецификация — это набор инвариантов, которым должны соответствовать код,
документация и процесс разработки. Инвариант — правило, которое остаётся
верным при любом изменении проекта и не отменяется ради удобства отдельной
задачи.

Спецификация отвечает на вопрос «что должно быть верно», а не «как это
сделать». Конкретные инструменты, библиотеки и структуры выбираются свободно,
пока не нарушают инварианты.

## Зачем она нужна

- фиксирует договорённости, чтобы не обсуждать их заново в каждом изменении;
- даёт явные критерии проверки вместо вкусовых оценок на ревью;
- сохраняет знания при смене разработчиков и потере контекста;
- отделяет устойчивые требования от сиюминутных решений.

## Требования к самой спецификации

Каждое требование в спецификации должно быть:

1. **Проверяемым.** Можно однозначно сказать, выполняется оно или нет.
2. **Обоснованным.** Указана причина, по которой правило существует. Правило
   без причины превращается в догму и устаревает незаметно.
3. **Стабильным.** Формулировка опирается на редко меняющиеся факты; всё, что
   меняется часто, выносится в README или в данные.
4. **Кратким.** Только то, что нельзя считать общеизвестным или вывести из
   кода. Спецификация не пересказывает документацию инструментов.
5. **Непротиворечивым.** Требования не конфликтуют друг с другом и с
   регламентом соревнования. При конфликте приоритет у регламента (см.
   [04_challenge_rules.md](04_challenge_rules.md)).

## Как пользоваться

- Перед изменением кода и документации сверяйтесь с применимыми инвариантами.
- На ревью проверяйте изменения по этим правилам, а не по личным
  предпочтениям.
- Если правило мешает решить задачу, сначала обсудите и измените
  спецификацию, а не обходите её молча.
- Новое правило добавляйте только вместе с причиной и способом проверки.
